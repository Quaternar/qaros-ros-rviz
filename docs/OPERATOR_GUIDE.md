# Operator guide

## The Qar Streaming panel at a glance

The plugin adds one panel to RViz, the class `qar_rviz_streaming/QarStreamingPanel`, which the configuration `qar_streaming_dev.rviz` loads under the name `"Qar Streaming"`. The panel is a status strip above six tabs, `Connection`, `"AR panels"`, `"AR tools"`, `Picking`, `Settings` and `Diagnostics`, and it shows the first of them at the start. The strip has two lines that stay in view on every tab: the state of the connection and the last error, `"Last error: <none>"` at the start. In a QarOS session the first line says what the State line of the group `"QAROS Hub"` says, `"QarOS: not connected"` at the start; in the offline preview it reads `"Qar runtime: STOPPED"`. Each line is cut to the width of the panel and keeps its full text as its tool tip.

The panel can stream itself into AR, and a change of the size of a streamed window makes the library rebuild the QarOS panel of that window. Nothing that the panel shows can therefore change its size. The size hints of the panel are measured once, from its tallest page; every page is a scroll area of its own with no horizontal bar; the status widgets cannot widen the dock; and the readout of the AR panels is a box of sixteen lines that never shows a scroll bar. When RViz restores a configuration that this version of the panel did not save, the dock gets a default size once, high enough for the tallest page. Half a second after RViz has shown the panel, the dock is fitted to its tallest page, so that no tab shows a scroll bar of Qt in AR; the fit only makes the dock higher, and it is skipped while an AR panel streams.

The panel keeps its settings in the RViz configuration: `File > Save Config` writes the values of 14 settings and a version number into the entry of the panel, and RViz hands them back when it loads the file. [Stream settings](#stream-settings) lists them and says which value wins.

Two buttons change their labels with the mode. The launcher `scripts\run_live_rviz_stream_real.ps1` sets `QAR_PANEL_LIVE_STREAM`, and with it the panel is live-capable: the button that starts the session is `"Connect to QarOS"` and the button that pauses it is `"Disconnect (pause)"`. Without that variable the panel is in the [offline preview mode](#offline-preview-mode), and the same two buttons are `"Start Qar"` and `"Stop Qar"`. The group `"Invite a device"` with the button `"Invite peer"` is on the tab `Connection` in both modes, and the simulated peers of the preview are added on the tab `Diagnostics`. The table lists the controls tab by tab, with the live label first.

## Connecting and pausing

`"Connect to QarOS"` joins the QAROS Hub. The press returns at once: the session owner, which runs on a thread of its own, loads the installed QAROS library and joins the Hub, and the render tick collects what the owner reports, so that RViz stays responsive. A QAROS call that can wait for the Hub, such as a query or a change of a panel or of the app volume, is queued for the thread of the owner and runs there, one at a time in the order in which it was queued, so that no such call runs on the GUI thread of RViz. The connection happens when you press the button and never when the panel loads. To the Hub the panel presents itself as the program `rviz2-plugin`, with the text `"RViz2 (QAROS ROS plugin) on "` followed by the host name.

**Which Hub.** The drop-down `"Hub:"` in the group `"QAROS Hub"` offers `Automatic`, `"This PC (approve once in the QAROS Hub)"` and `"Another PC (pairing code)"`. Automatic takes the Hub of another PC when a pairing with it is stored, else the Hub of this PC when QAROS is installed here, else the Hub of another PC. The choice is a setting (`"Hub Mode"`, with the variable `QAR_PANEL_HUB_MODE`), and a new choice is passed to the owner and applies at the next connect. [QAROS Hub and sessions](https://docs.quaternar.com/docs/next/developer-guide/onboarding-and-sessions/) and [Source applications](https://docs.quaternar.com/docs/next/operator-guide/source-applications/) describe the onboarding from the side of QAROS, and [Connection panel](https://docs.quaternar.com/docs/next/user-guide/connection-panel/) the Visualizer side of it.

- **This PC.** The Hub asks the person at the PC, in a window of QAROS, whether the program may join, and the State line says `QarOS: waiting for approval in the QAROS Hub - click Allow in the QAROS window` with the time that is left. The wait is 120 seconds unless `QAR_PANEL_APPROVAL_TIMEOUT_S` gives 0 to 600. The plugin writes no pairing for this mode. No code is typed, and the group `"Invite a device"` works only in this mode.
- **Another PC.** Type the host name or address of that Hub in `"Host:"`, its onboarding port, which that Hub shows next to the pairing code, in `"Port:"`, and the code in `"Code:"`, and press Enter or `Pair`. `"Port:"` takes 1 to 65535 and `"Code:"` at most 16 characters. The code lives about ten seconds and works once, so type it as soon as the Hub shows it; the field is cleared when you submit. The pairing is stored in the file `identity.txt` of the identity folder, and the next connect rejoins with it and asks for no code. `"Forget pairing"` erases it and needs a second click within five seconds, and the button reads `"Click again to forget"` in between; it is grey in the mode This PC, where the approval is revoked in the Visualizer. `Cancel` ends a wait for the approval, a rejoin or a pairing.
- **The identity folder** is `%LOCALAPPDATA%\Quaternar\QarOS-ROS\rviz2-plugin`, with the value of `QAR_PANEL_INSTANCE` after a dot when it is set, so that two copies of RViz do not share a pairing; `QAR_PANEL_IDENTITY_DIR` replaces the folder `%LOCALAPPDATA%\Quaternar\QarOS-ROS`. The identity folder also holds `runtime`, the storage folder that the session owner gives to QAROS in every mode.

The line `"Identity:"` says who the Hub knows: `"This PC: approved local app ("` followed by the program name in the mode This PC, and `"Paired with "` followed by the host, the port and the first eight characters of the pairing id, or `"Not paired"`, in the mode Another PC. When a join fails, the State line and the label `"Last error: <none>"` say why in a plain sentence that begins with `QarOS: `, for example that QAROS denied the app, that nobody answered the prompt in time, that the Hub is not running, or that the code was wrong or has expired, and `"Connect to QarOS"` is on again.

When the join is complete, the panel makes its render factory and the app volume of the session on the thread of the owner, and the State line reads `QarOS: joined (local app) - setting up the session ...` until that is done. Then the streaming of the 3D scene starts, the plugin subscribes to the click and hover gestures of the app volume, and the panel writes that a stream opens for each target that is online. The State line then reads `QarOS: connected (local app) - 1 target(s), 1 served`, or `(paired)` for the Hub of another PC, and the plugin serves the page of [the AR control panel](#the-ar-control-panel) unless you switched it off. The hidden Displays panel is made as soon as the first stream of the 3D scene is open, unless you switched it off. The connection invites nothing, so a target needs no invitation: a Visualizer that you opened in QAROS and that has a receiver is a target by itself.

`"Disconnect (pause)"` stops the streaming of the 3D scene and keeps everything else: the session stays open, and the render factory, the AR panels, the AR tools and the AR control panel stay as they are. The State line then reads `streaming paused`. Pressing `"Connect to QarOS"` again resumes the streaming at once, with no new join. A pause while the app volume is still being made gives the session back instead. Everything that was built on the session is released, in the order that QAROS requires, only when `"Forget pairing"` is confirmed, when the session ends on its own, and when RViz closes the panel; the AR panels are then hidden and let go, never closed, as [Closing panels](#closing-panels) says.

When every runtime peer of the Hub is gone for more than three seconds, the State line reads `QarOS: Hub not reachable - waiting for it to come back`, and nothing is torn down; this is a heuristic. A call on the GUI thread that takes longer than 20 ms is logged as `[qar-gui-call] WARNING` (`QAR_GUI_CALL_WARN_MS` changes the limit), and the owner thread logs a QAROS call that takes 500 ms or more and a task that takes one second or more.

Only the join to the Hub of this PC was exercised in live sessions; the answers Deny and no answer, a Hub that stops while the panel is connected, the pairing with the Hub of another PC, forgetting a pairing and the invitation of a device are described from the code and the unit tests and have not been run in a live session.

## Targets and invitations

A target is a device or an application that receives a stream: in the Hub, a peer with the role target that is online, or whose presence the Hub has not yet decided, and that is not this program. Each target gets its own stereo stream of the scene, rendered from the head pose that QAROS reports for it. A peer that is offline, leaving or retired is gone, and its stream stops. At most 8 targets get a stream, and `QAR_PANEL_MAX_PEERS` sets another number; a target beyond it is listed as not served, with the reason `"cap reached"`. The list `"Targets:"` of the group `"QAROS Hub"` shows each one as its name, its kind and its presence, followed by `served` or `not served`.

The group `"Invite a device"` asks the Hub of this PC to start the app of a device, which then joins as a target. The drop-down offers `"HoloLens 2"` and `"Headset (Quest, Android)"`, and for both the field next to it must hold the host name or address of the device; without it the panel answers `Invite peer: type the host name or address of the device in the field next to the device selector.` The button is grey unless the panel is joined to the Hub of this PC and streaming, and its tool tip says what it needs; a Hub of another PC refuses invitations, so the device is added in the Visualizer there. The press returns at once, the button reads `"Inviting..."` until the answer of the Hub arrives as an event, and the panel then logs the invitation or the reason why it failed. A simulated peer has a button of its own on the tab `Diagnostics`.

**Invitations at connect.** `QAR_PANEL_INVITE_PEERS` holds entries of the form `kind:hostname`, separated by commas, with the kinds `hololens` and `headset`, and the launcher parameter `-InvitePeers` fills it. The plugin reads it when the session first connects, handles it once for that session, and ignores it for the Hub of another PC. An entry that fails is logged and skipped, so that one unreachable headset does not stop the others.

The list of the group `"Simulated peers"` on the tab `Diagnostics` shows only the simulated peers of the preview; the heartbeat shows one field for each stream of QAROS.

## Stream settings

The tab `Settings` holds the settings of the streams and of the session in three groups, and the titles of the groups say when a setting takes effect. The group `"Streams (apply to new streams)"` has the size and the rate of the pictures. `"Resolution:"` offers 640 x 480, 1024 x 1024, 1280 x 720, 1600 x 900, 1920 x 1080 and 2048 x 2048, and starts at 1280 x 720; `"FPS cap:"` offers 15, 30, 60, 72 and 90 frames per second, and starts at 60. Both are read when a stream is created, for each new peer, and they do not resize a stream that exists. The scheduler renders the due streams that fit the budget in one batch, under one render lock, so that every peer sees the same snapshot of the scene. A batch gets a budget of about 16 ms: frames of peers beyond the budget are shed for that tick, except that a due peer that was not rendered for 1/30 s is always served, and the heartbeat counts the shed frames as `budget_skips=`. Every peer costs four scene renders per frame, a colour render and a depth render for each of its two eyes, so choose a lower resolution when you serve several headsets.

The group `"Session (apply when you connect)"` has two check boxes. `"Start the hidden Displays copy when connecting"` decides whether [the hidden Displays panel](#the-hidden-displays-panel) is made by itself, and `"Show the AR control panel when connecting"` whether the page of [the AR control panel](#the-ar-control-panel) is served; both apply at every connect. The Hub is chosen in the group `"QAROS Hub"` of the tab `Connection`, which [Connecting and pausing](#connecting-and-pausing) describes. The check box `"Show advanced options"` is the last control of the tab. It shows the group `"Advanced"` and, in a QarOS session, the group `"Simulated peers"` of the tab `Diagnostics`, and its state is not saved. The group `"Advanced"` has `"Prime next frame"`, the choice `"Closed AR panels:"` between `"Close them"` and `"Show a notice"`, and the check box `"Hide panels in AR instead of closing them (experimental)"`; [Closing panels](#closing-panels) says what the last two do.

**Saved settings and variables.** RViz keeps 14 settings of the panel in its configuration, under the settings version 3: the resolution, the frame rate cap, the mode, the host and the port of the Hub, the start of the hidden Displays copy, the AR control panel, the close mode of the AR panels, the choice between hiding and closing, the scale of the AR tools, the target and the frame of the picks, and the kind of device and the host name of the invitation. For each of them the value in force is the first of three: the environment variable of the setting, when it is set, not empty and acceptable; the value saved in the RViz configuration, when it is acceptable; the default. A control whose variable wins shows that value and is grey, and its tool tip names the variable. The saved configuration never takes a value that only the variable supplied, so removing the variable brings the choice of the operator back. A variable that is not acceptable is logged once with the line prefix `SETTINGS:` and ignored. A configuration of an older version loses the key `"Peer Admission"` when it is loaded, because every target gets a stream, and the invitation kinds `quest`, `visualizer` and `zed` are read as `headset` or `hololens`; the log says so with the prefix `SETTINGS:`. The variables of earlier versions of the plugin that have no effect any more are ignored and logged as `ignored: <name> has no effect with this QAROS`. The pick mode, the check box `"Publish without confirming"`, `"Prime next frame"`, `"Show advanced options"`, the simulated peers and the selected tab are never saved, so that a gesture cannot move a robot because a switch was left on.

**The render tick.** The panel has no control for the period of the timer that drives everything that the panel does each frame: the heartbeat, the AR panels, the AR tools, the spatial picks, the floor plane and the streams. The period is 0.1 ms unless `QAR_PANEL_TICK_MS` gives another one, and the log line `Render tick: <ms> ms` says which of the two applies. The timer is always a precise timer of Qt, because the coarse timer is served from the system tick of Windows of about 15.6 ms and would turn even a period of 16 ms into about 31 ms. A timer cannot have a period below 1 ms, so the default of 0.1 ms runs a timer without an interval, which fires whenever the event loop is idle, and the body of the tick runs at most once in each 100 microseconds.

`"Prime next frame"` decides when the wait for the next frame of QarOS starts. On, which is the start value and the default of `QAR_ADAPTER_PRIME`, the wait starts right after a frame was shown, so that one tick serves one frame. Off, the wait starts at the next tick, so that two ticks serve one frame. The switch is live: it applies at once, with no restart. It tells a wait that the render tick causes apart from a mismatch of the SDK, and it does not change the frame budget of a peer, which still decides how often the peer is due. The heartbeat shows the values in use as `tick=` and `prime=`.

## AR GUI panels

The tab `"AR panels"` streams a Qt window of RViz as a QarOS GUI panel. The drop-down lists what can be streamed: first `"This QAR panel"`, then every dock of RViz by its title, then one entry `Video: <topic>` for each video panel that an AR tool opened, and last the hidden Displays copy. An entry whose AR panel is parked carries the words `"(parked in AR)"` after its title. The list is filled when the panel loads and once more at the next turn of the event loop; `"Refresh"` fills it again and logs how many windows it found, so press it after you add a dock.

`"Stream panel to AR"` starts the stream of the selected entry and `"Stop streaming"` ends it. The press does no call into QAROS: the QAROS panel is created on the next render tick, once the widget is laid out, and the calls into QAROS that make it are queued for the thread of the owner, so that RViz does not stand still. A panel hangs by its top edge. The top edge of the first panel is 1.5 m above the origin of the room and 1 m in front of it, each further panel hangs 0.65 m further along the x axis, and no panel reaches lower than 0.10 m above the RViz ground. With `QAR_PANEL_FIXED_POSES` set to `ground`, which the live launcher does unless your shell sets a value, the top edge hangs 1.5 m above the RViz ground, wherever you moved the scene to. The place is fixed because no call of QarOS asks where the operator is: the pose of the viewer comes only with a render sender, and the plugin uses it only to place the AR control panel. A panel is captured at 15 frames per second at most, and at 30 when its dock holds an Image or Camera display.

Before a dock is streamed, the plugin fits it to its content, so that its AR copy shows no scroll bar. It makes the dock higher in up to six rounds, never makes a dock that streams smaller, and ends the fit when two looks in a row agree. When the dock shares its column with others, the RViz window is asked for the missing height unless it is maximized or full screen, and it never grows beyond its screen. The AR panel appears when the fit is over, and `"Disconnect (pause)"` or closing the dock cancels a start that waits. A dialog that RViz opens is measured before its AR panel is made, so it may open a little taller on the desktop, and it is moved up when it would otherwise reach below the screen. The log lines that begin with `"PANEL SIZE:"` and `"AR PANEL:"` say what the fit did, and [AR panel lines](LOG_REFERENCE.md#ar-panel-lines) lists them.

A panel keeps one QAROS name for as long as its window keeps its key: the name is made from the key, a hash of the key, the program, the instance and the host, so that a window that is streamed again, in this session or in the next, finds its QAROS panel by that name. A panel that is started again under a title that an earlier AR panel of the same RViz process used carries a number after the title, when the earlier panel was closed: the second start of the dock Views is titled Views (2), and the third Views (3). The key of the panel and the entries of the list do not change, and the count lasts until RViz is restarted. While hiding is on, which is the default, `"Stop streaming"` hides the AR panel and starting it again shows the same QarOS panel, so no panel is closed or made again and no title is numbered; [Closing panels](#closing-panels) has the details. When the hidden Displays panel is started again after a close, the Visualizer of an earlier QAROS runtime crashed in every case that the authors of qar_rviz_plugin observed, with a numbered title as well, and it crashed at times when another panel was closed or created; QAROS started a Visualizer again after several seconds, during which the 3D streams stood still. Do not close and start panels in quick succession, and wait for the Visualizer to come back before you press the next button. [The Visualizer crashes when the hidden Displays panel is started again](TROUBLESHOOTING.md#the-visualizer-crashes-when-the-hidden-displays-panel-is-started-again) has the details.

The readout of the tab starts as `"AR panels: none"` and shows live counters while a panel streams; it is refreshed up to four times a second. The box shows the heading, two lines of totals and one short line for each panel, and it ends with `"... and %1 more panel(s); all counters are in the log"` when the lines do not fit its sixteen lines. The first line of totals has the form `input: in %1, missed %2, dropped %3`, followed by the last reason of a drop: it counts the samples that came from the input source, those that pointed at no panel and those that the state machine refused, and an `in` of 0 means that the runtime sends nothing. The second line begins with `panels: live=%1` and goes on with `(hidden %1)` for panels that are hidden in AR, `(parked %1)` for those among them whose window closed, ` closed=%1 (destroyed) notice=%2`, and `arclosed=` when the operator closed a panel in AR. Each panel line has its key, the size of its buffer in pixels and the frames that were sent, followed by the words that apply: `notice`, `"closed in AR"`, `parked` or `hidden`, `"widget hidden"`, `"waiting for a receiver"`, `"rebuilds %1"` for a panel that was rebuilt more than once, which is the sign of a window that changes its size, and `error:` with the last error of the panel. The sizes in metres and the counts of the input of each panel are in the heartbeat of the log.

A click and a hover in AR reach the real widget of RViz as Qt events, which includes the lists of drop-down boxes and the dialogs that the widget opens. A dialog becomes a panel of its own in AR, placed 0.5 m further along the x axis than the panel that opened it. The authors of qar_rviz_plugin confirmed the click, the hover, the drop-down lists and the dialogs in earlier live sessions, held with builds for a QAROS runtime earlier than 0.9.0-dev.3008+65dc9aeb; the dialog of the hidden Displays panel opened in AR in the live checks with 0.9.0-dev.3008+65dc9aeb, also on a panel that was found again; the drag of a slider and the use of two hands are covered by unit tests, the tap count and the long press by neither a unit test nor a live session, and no live session has checked any of the four; [What the live sessions showed](VERIFICATION.md#what-the-live-sessions-showed) lists the evidence. [The hidden Displays panel](#the-hidden-displays-panel) and [Closing panels](#closing-panels) describe the two cases that need more.

### The AR control panel

The AR control panel is a web page with big buttons that hangs in front of each user in the headset, so that the user can switch panels and tools and pick in the scene without the desktop. The page is titled `QAR control`. From the top it offers the choice `Off`, `Point` or `"Nav goal"` for picking in the scene with the buttons `"Confirm pick"` and `"Cancel pick"`; the state of the connection, which reads `Connected`, `Connecting`, `"Paused on the desktop"`, `"Not connected"` or `"Offline preview"`; a switch for each of up to six panels of the tab `"AR panels"`, and one for each of up to four AR tools, with a line that says how many more there are; the number of peers; and the last error. The standard Displays dock of RViz has no switch on the page: its AR copy, the hidden Displays panel, is in the list instead, and the line that says how many more panels there are does not count the dock. A switch hides or shows the AR panel of a window, or of a tool, and the plugin carries it out on the next render tick; a pick command runs at once and goes through the same code as the controls of the tab `Picking`, so the tab shows the mode that the page armed, and confirming and cancelling work as on the desktop. A command that the plugin refuses, for example a confirmation with no pick waiting, is answered on the page with the reason, the page's whole state is sent again, and the answer clears itself after about six seconds. Each user gets a panel of their own, visible to that user only, one metre ahead of the head along the gaze, 0.35 m to the right and with its top edge 0.10 m below the eyes, standing upright and facing the user; it is placed once, when the first eye poses of the stream of that user are known, and never moved. `QAR_PANEL_AR_CONTROL_PER_PEER` set to `off` gives one shared panel for everybody instead; it waits up to 20 s for a head pose and otherwise hangs at a fixed place. `QAR_PANEL_AR_CONTROL_FLIP` set to `on` turns the panel round by half a turn, for a runtime that shows its back.

On the desktop the group `"AR control panel"` of the tab `Connection` shows whether the panel exists and for whom, `"Show AR control panel"` asks QarOS to show it again after it was closed in AR, and `"Copy page URL"` copies the address of the page, which a desktop browser opens as well. The page needs the web server of the AR tools, so it is served on the same host and port, behind a token of its own. In the offline preview only the page is served and there is no QarOS panel; the page then shows no switches and says `AR panels and tools are switched in a live QarOS session`. The setting `"Show the AR control panel when connecting"` and the variable `QAR_PANEL_AR_CONTROL` switch the whole feature off.

## The hidden Displays panel

When the first stream of the 3D scene is open, the plugin makes a second instance of the Displays panel of RViz, shows it off-screen only, and streams it into AR as `hidden:Displays` with the title `"Displays (AR)"`. A start after a close in the same RViz process gives the copy a number after the title, Displays (AR) (2) for the first restart and Displays (AR) (3) for the next, and `"Disconnect (pause)"` does not reset the count. While hiding is on, which is the default, `"Stop streaming"` hides the AR panel of the copy and `"Stream panel to AR"` shows the same panel again, so nothing is numbered. At a restart after a close the Visualizer has crashed in every case that the authors of qar_rviz_plugin observed, and QarOS starts it again after several seconds; [The Visualizer crashes when the hidden Displays panel is started again](TROUBLESHOOTING.md#the-visualizer-crashes-when-the-hidden-displays-panel-is-started-again) says what to do. The copy is bound to the same display tree as the real Displays dock, so a check box that you toggle, a property that you edit, and a display that you add, remove or rename in the headset change the displays of RViz. The AR panel hangs at x = -1.2 m and z = -1.0 m, with its top edge at the height that `QAR_PANEL_FIXED_POSES` gives, and the dialogs that it opens, such as the one of its `Add` button, are placed 0.5 m to its +x by the manager.

The copy never reaches your desktop. It is shown with the Qt attribute that maps a window without putting it on the screen, it does not accept keyboard focus, so that its shortcuts cannot fire and it cannot take the foreground from RViz, and it does not keep RViz alive after the main window closes. The drop-down lists, menus and completer lists that it opens appear in AR and never on the desktop, because the plugin keeps every popup of an off-screen panel off the screen; tooltips on Windows are not covered. Dialogs are the exception: they stay ordinary windows and also become AR panels. The dragging of items is switched off on the copy, because a drag that began with input from AR must never enter the drag and drop of Windows.

| Setting | Meaning |
|---|---|
| `QAR_PANEL_HIDDEN_DISPLAYS` | `off`, `0`, `false` or `no` stops the automatic start on connect, and the panel says so once; the entry of the drop-down still starts the copy by hand; the default is on, and the check box `"Start the hidden Displays copy when connecting"` of the tab `Settings` is the same switch |
| `QAR_PANEL_HIDDEN_DISPLAYS_SIZE` | the size of the copy in logical pixels as `WIDTHxHEIGHT`; each side is limited to 200 to 2000, a text that is not a size keeps the default, and each correction is logged as a warning; without a size the copy starts at 480 by 756 and is fitted to its display tree |

The size of the copy is read once, with the widget, and never changes after the copy streams, because a change of size would rebuild the sender. Unless a size is set, the plugin fits the copy to its display tree before it streams: it makes the copy as high as the rows of the tree need, from 400 to 1400 pixels, hides the help area at the bottom of the panel, and streams the copy when the fit is over, so that its AR panel shows no scroll bar. The last entry of the drop-down of the tab `"AR panels"` always offers the copy, whether or not it exists yet. `"Stream panel to AR"` on it creates the widget the first time and starts the stream, and later it starts the stream again. `"Stop streaming"` ends the stream only: the widget stays alive and off-screen, so that the next start finds it. When you close the panel in AR, the stream entry stays, because the window of the copy is never closed, and `"Stream panel to AR"` clears that entry before it starts the stream again. `"Disconnect (pause)"` leaves the copy streaming like every other panel.

If something hides the copy, for example a call of `hide` or `close` on it, the plugin shows it off-screen again at the next tick and logs this once, because a hidden widget would stream a blank rectangle. A failure to make the copy is logged with its reason, and the plugin carries on without it. [Hidden Displays panel lines](LOG_REFERENCE.md#hidden-displays-panel-lines) lists the lines.

## AR tools from the ROS graph

An AR tool is a panel that the plugin generates from a topic, a service or an action of the live ROS 2 graph and serves as a web page, which the browser of QarOS opens as a URL panel. The plugin needs no generated message code: it reads the layout of a type from the introspection typesupport of the interface package at run time, picks a template for the type, and binds the controls of the page to the fields of the type.

**The dialog.** `"Add from ROS graph..."` opens the modal dialog `"Add from the ROS graph"`. It lists the topics, services and actions of the graph as trees by namespace with their types, under the headings `Topics`, `Services` and `Actions`. The field `"Filter:"` narrows the list by a part of a name, of a type, or of the kind word, so that `"service"` shows only the services, and `"Refresh"` asks the graph again and keeps your selection. A double click on an entry does the same as `"Add"`. For a topic, `"Add"` creates the RViz display that accepts the type and pins the topic to the list of watched topics; `"Remove topic"` forgets a watched topic and leaves its display alone.

The check box `"Expose as a QAR AR tool"` generates the AR panel. For a service and for an action it is always on and cannot be changed, because RViz has no display for either. The check box `"Allow publishing from AR"` exists for topics only: it is off at the start and enabled only when the topic is exposed, because a publication to a topic is a command to a robot. The lines under the tree say what `"Add"` will do before you press it: which display it creates or that none is created, and whether the AR panel is read-only or has a publish form. An exposed topic of type `sensor_msgs/Image` or `sensor_msgs/CompressedImage` gets no RViz display at all, because exposing a topic as an AR tool must not add a display that you did not ask for.

**Where the page is served.** The first tool starts a web server in RViz, and the panel logs where it listens. The server listens on all network interfaces, so that a headset on the network can reach it, on a port that the operating system picks, so that two RViz instances on one machine do not collide. `QAR_PANEL_WEB_PORT` pins the port, for a firewall rule, and `QAR_PANEL_WEB_HOST` sets the host name that the addresses of the pages contain. A panel is reached at `http://<host>:<port>/p/<token>/`, and a wrong or missing token gets a 404. The address starts with `http://`, the traffic is not encrypted, and the token of 128 random bits is the only protection. [Network prerequisites](GETTING_STARTED.md#the-same-on-hololens-2) lists what the network has to allow.

**The list of tools.** Each tool is a row of the list: the kind, the name and the type, followed by `"[in AR]"` when its QarOS panel exists, `"[hidden in AR]"` when that panel is hidden or `"[pending]"` when it does not exist yet, and by `"[writable]"` for a tool that may publish. The label under the list says how many tools exist and where the pages are served, and it carries the viewport that the last page reported. The tooltip of a row has the address of its page, the template that laid it out, and the last error. The buttons act on the selected row:

- `"Remove tool"` forgets the token first, so that a page that reconnects meets a 404, drops the subscription or the publisher, removes the row, and takes the AR panel out of use: with hiding on the panel is hidden and kept until the session ends, and exposing the same tool again takes it over, and with hiding off it is closed.
- `"Re-open in AR"` brings the AR panel back, after a restart of the session or when the panel was hidden or closed in the headset. With hiding on, QarOS is asked on the next tick to show the panel again, and when it refuses, the log and the last error say so and nothing is closed or made again; with hiding off, the panel is closed and made again. The page and its token do not change.
- `"Copy URL"` puts the address of the page on the clipboard, to open it in a browser of the desktop while you debug.
- The spin box with the prefix `size x` is a multiplier from 0.25 to 4.00 on the size that the plugin derives from the page. It starts at the value of `QAR_PANEL_WEB_SCALE`, or at 1.00, and it applies with the next `"Re-open in AR"` and with the next placement of the panel. `QAR_PANEL_WEB_SIZE` pins the size in metres.

The size of a tool panel comes from its page and from a fixed design viewport, not from the viewport that the browser reports. The plugin measures the page for a viewport of 500 by 500 CSS pixels, the size of the AR control page, which is a panel of 0.55 by 0.55 m, and the page shrinks its theme and drops columns to fit it. The page still reports the viewport that QAROS gave it, and the plugin logs the report; under the installed QAROS the viewport follows the size of the panel, so a size taken from the report would feed back into itself. The panel is placed again only when its size moved by more than 5 mm, at most 3 times in 10 seconds and never to a width below the floor of 0.25 m, and a refused resize is logged and leaves the panel as it is. The top edge of the first tool hangs at the height that `QAR_PANEL_FIXED_POSES` gives, 1.5 m above the origin of the room or the RViz ground, and 1.2 m in front of the origin, and each further tool hangs 0.7 m further to the left. A page that is taller than its viewport is reached with the buttons of a pager and not with a scroll bar, because a scroll bar is a poor target for a hand ray.

**The templates.** A semantic template lays out the types that it claims, and a type that no template claims gets the generic form, which has one widget for each field. A semantic template scores 100 and the generic form 1, so that a template always wins for its types. A template whose probes do not recognise the interface definition of the installed distribution hands the type to the generic form. The plugin registers these 17 templates:

| Template | Claims | Layout |

| `pose` | `Pose`, `PoseStamped`, their covariance forms, `Point`, `Point32`, `PointStamped`, `Quaternion`, `QuaternionStamped`, `Transform`, `TransformStamped` | position, orientation as angles and as a quaternion, frame and stamp |

The service answers every call with success and the message `trigger <n>`, where `<n>` counts the calls, and the script prints a line for each call. The script ends by itself after `--seconds` seconds, 1500 by default, so that no process has to be stopped. It needs the environment of the ROS 2 distribution that `scripts\env_setup.ps1` imports, and it reaches RViz only when its shell has the same `ROS_DOMAIN_ID` as the session of RViz. The clean-up of the live launcher with `-Confirm` stops only the Python processes whose command line names `publish_test_markers.py`, `publish_test_tf.py`, `publish_test_robot.py` or `publish_test_pointcloud.py`, so it leaves this script running. To try it, prepare a window of its own with the two lines below: the first goes to the folder of the clone, and the second, with the leading dot and the space, imports the environment of the ROS 2 distribution.

```powershell
Set-Location "$env:QAR_ROOT\src\qar_rviz_plugin"
. .\scripts\env_setup.ps1
```
```text
...
=== Qar RViz2 environment set up in this PowerShell session ===
...
python  -> C:\qar\venv\Scripts\python.exe
...
```

In that window run `python scripts\publish_template_topics.py` with `--seconds 600`, then open `"Add from ROS graph..."`, type `qar_demo` in the field `"Filter:"`, select a topic or the service, tick `"Expose as a QAR AR tool"` for a topic and press `"Add"`; the tooltip of the new row names the template that laid the page out.

A panel is limited to 48 fields for each section and a depth of 4 levels, and what does not fit is reachable in a widget that shows all fields of the section as raw JSON. An array that the plugin pushes to a page is cut to 256 elements, so that the large arrays of a message do not travel to the page.

**Who may write what.** The data document of a panel has the sections `msg`, `draft`, `request`, `response`, `goal`, `feedback`, `result` and `status`; only `draft`, `request` and `goal` are writable, and `draft` exists only when you allowed publishing. The plugin refuses a control event of a page when the widget id is unknown, when the frame names another action than the widget declares, when the action id is unknown or does not apply to the entity, when it writes into a read-only section, and when the value does not fit the schema, and it answers with the reason and logs a line that begins with `"AR CONTROL: refused"`. A refused edit changes nothing. The buttons `Publish` and `"Send goal"` ask for a second press within 4 s, and the label of the button says `"Press again to confirm"`; `"Call service"` and `"Cancel goal"` act on the first press, and cancelling is the safe direction. A button may carry a payload, as the stop button of the velocity template does, and then it sends that message in place of the staged one, after the same validation; the stop button asks for no second press and publishes its all-zero command on the first press.

**How the data moves.** The page of a topic is refreshed at 5 Hz, however fast the topic is, because a person reads a value more slowly: the subscription keeps only the newest message, and the plugin converts it on the tick. A call of a service and the goal of an action are asynchronous, and the plugin never waits for the answer; the page shows the outcome of the call and, for an action, its feedback, its status and its result. All of this runs on the GUI thread of RViz, on the node that RViz spins, so that no thread of its own exists.

## Video in AR

A topic of images reaches AR in two ways. The first is the button `"Open video in AR"` on the page of an exposed image topic, which opens a new AR panel, titled with the topic, that shows the video. The panel has the key `video:<topic>`, it appears in the drop-down of the tab `"AR panels"` as `Video: <topic>`, and `"Stop streaming"` hides it with hiding on and closes it otherwise. The panel is made when the first frame of the topic arrives, so that it has the size of the camera from the start and is not in the list before. The second way is a dock of RViz that holds an Image or Camera display: the render window of such a display cannot be captured, so the plugin subscribes to the topic of the display and streams the video into the AR panel directly. A Camera display is shown without the 3D overlay behind the image, and the panel says so in the log.

Both ways receive the topic in a private ROS 2 context, a DDS participant of its own, so that the Image display of RViz cannot starve the video. The QoS follows the publishers: the subscription is reliable when every publisher is reliable and best effort as soon as one publisher is not, with a history depth of 2. A topic that both ways receive uses one subscription and one decode. The video is decoded on a thread of its own into a slot that holds only the newest frame, so that a late frame is replaced and never queued. The panel runs at up to 30 frames per second.

The plugin decodes the encodings `rgb8`, `bgr8`, `8UC3`, `rgba8`, `bgra8`, `8UC4`, `mono8`, `8UC1`, `mono16`, `16UC1`, `32FC1`, `yuv422`, `uyvy`, `yuyv` and `yuv422_yuy2` of `sensor_msgs/msg/Image`. A `sensor_msgs/msg/CompressedImage` is decoded when its data is PNG or JPEG, which the first bytes of the data decide whatever the `format` string says; any other format is refused, whatever Qt plugins are installed. A frame larger than 1280 by 1280 pixels is scaled down to fit and never scaled up. The plugin reads the type that the topic advertises, `sensor_msgs/msg/CompressedImage` first and then `sensor_msgs/msg/Image`, and when no publisher exists it takes a topic whose name ends with `/compressed` for compressed images and any other topic for raw images.

Large video topics need the Fast-DDS profile `scripts\fastdds_large_data.xml`, which the launcher exports and which `scripts\publish_video_file.py` applies to itself. With the default segment of 512 KB of the shared-memory transport, 5 to 8 percent of the frames of a 6 MB stream lose fragments, and the repair of a lost fragment delays the same frame for every reader; the profile enlarges the segment to 64 MB. The launcher parameter `-TimingCsv` sets `QAR_VIDEO_TIMING_DIR` to a fresh folder, and the plugin then records the timing of every stage into CSV files there. `scripts\analyze_video_timing.py` reads those files and attributes a stall to the publisher, to the plugin or to QarOS; [Timing CSV files](LOG_REFERENCE.md#timing-csv-files) describes the files. A video that has stopped is no stall: the panel submits its last picture again once a second, and the analyzer leaves those idle gaps out and reports how many it ignored.

## Closing panels

What happens to an AR panel when its window goes away depends on the choice between hiding and closing. With hiding on, which is the default, nothing is closed while a session runs: the AR panel is hidden and parked, capture stops and input is dropped, its QarOS panel, its video sender and its subscriptions are kept until the session ends, and starting the window again shows the same panel. When the session ends, the AR panels that are hidden stay hidden in the Hub, under their names, and the plugin lets go of them; the next session finds each one by its name and shows it again, so that nothing has to be closed. The reason is that every close of a QarOS panel in the middle of a session that the authors of qar_rviz_plugin tried with a web panel open crashed the Visualizer of an earlier QAROS runtime, and a creation did not. The setting `"Hide panels in AR instead of closing them (experimental)"` and the variable `QAR_PANEL_AR_VISIBILITY` choose between `hide` and `close`.

With closing, the close mode applies, which `QAR_PANEL_CLOSE_MODE` or the choice `"Closed AR panels:"` selects. `destroy` is the default: the AR panel is closed, its video sender is destroyed, and the stream is forgotten. `notice` keeps the AR panel as a notice that says that the window was closed, and keeps the video sender until the session ends. At the end of the session the mode `destroy` closes each panel once, and the other modes hide the panels and detach them. The mode `notice` exists as an escape for a QarOS runtime that does not survive the destruction of a sender in the middle of a session. The vendor states that destroying a video sender while a session runs is safe in the current binaries, and crash dumps from before that statement exist. The panel takes the mode when the first panel is streamed and again whenever one of the two choices changes, and the line `AR PANEL: close mode` says which mode is in force and where it came from; a change is acted on by the closes that follow. A text of `QAR_PANEL_CLOSE_MODE` that is not a mode is refused with a warning and the saved choice or the default stays in force.

| Cause | What the plugin does |
|---|---|
| `"Stop streaming"` | closes the stream through the close mode, which with hiding on parks it; when the click was pressed in AR on the very panel that it stops, the teardown waits until the click has returned |
| the dock of a streamed window is closed in RViz | closes the stream in the same way; showing the dock again does not restart it, so press `"Stream panel to AR"` |
| the widget of a streamed window is destroyed | closes the stream at the next tick, before anything is captured |
| a streamed dialog is dismissed | retires its panel as soon as the dialog hides, closes or is destroyed; with hiding on, the panel is parked and the same dialog shows it again |
| the operator closes the AR panel in QarOS | skips the close call of QarOS, stops the capture, marks the panel `"closed in AR"`, and counts it as `arclosed=` in the heartbeat |
| a closed `Video: <topic>` panel in `destroy` mode | also drops the ROS subscription and the row in the drop-down |

A panel that is started again after it was closed gets a number after its title, as [AR GUI panels](#ar-gui-panels) says. A parked panel is not numbered, because its start creates no QarOS panel; the same holds in the mode `notice`, where a start brings the notice panel back to life, and no Visualizer crash occurred in the 4 restarts that the authors of qar_rviz_plugin tried in that mode. The price of `notice` is a notice panel in AR for each closed window, which you close in AR. A session keeps up to 16 panels that are parked or show a notice; beyond that, a window that is streamed for the first time is refused until the session ends, and the heartbeat counts the refusals in the field `"CAPPED"`. Close and start panels at a calm pace: a quick burst of closes and starts once gave a black scene in trials of the authors.

A change of the size of a streamed window, which a drag of the border of a dock causes, keeps its QarOS panel: the library detaches the video sender and attaches a new one of the new size to the same panel, which keeps its name. A new size is adopted only when it differs by at least 8 pixels and has held for half a second and for three ticks. `QAR_PANEL_RESIZE` set to `new-panel` makes a second panel for the new size instead, hides and keeps the old one, up to 32 such panels in a session, and a sender that cannot detach takes that way as well.

QarOS can refuse to hide or to show a panel. With hiding on, the panel then stays as it is, nothing is closed and nothing is made again, and the plugin reports it with the line prefix `"AR VISIBILITY:"` and in the label `"Last error:"`. With closing, a panel that cannot be hidden is closed through the close mode, and one that cannot be shown is closed and started again, except in the mode `notice`, where it is left as it is.

In `destroy` mode a close writes a line that says that the close was requested. The library of Qt writes one line that begins with `closed`, with the frames served, the reason and the outcome of each step, and the adapter writes the three steps with a time of its own: the subscriptions are cancelled, the QarOS panel is closed or the close is skipped because the operator already closed it, and the video sender is destroyed. With hiding on, a close writes a line that begins with `"AR PANEL:"` and says that the panel is parked, and the hide and the show that QarOS carries out write lines that begin with `"AR VISIBILITY:"`. [AR panel lines](LOG_REFERENCE.md#ar-panel-lines) lists them. The heartbeat counts `closed=` for the panels that were closed and destroyed, `notice=` for those that show a notice, `hidden=` for those that are hidden and `parked=` for those that are parked, and a failure of the close call appears as a field named `"CLOSEFAIL"`.

## Spatial picking

The tab `Picking` turns the pointer of the headset into ROS messages. Arming is explicit: the mode starts at `Off`, so that a gesture can never move a robot because a mode was left on. `Mode` chooses what a pointer means in the 3D scene, `Target` what it is resolved against, and `Frame` the frame in the header of every published pick, `map` at the start. The plugin subscribes to the click and hover gestures of the app volume of the session when it connects; a session without an app volume subscribes to nothing, and the panel logs that.

| Mode | Gesture | Topic | Type |
|---|---|---|---|
| `"Pick a point -> /clicked_point"` | a click | `/clicked_point` | `geometry_msgs/msg/PointStamped` |
| `"Set a navigation goal -> /goal_pose"` | press to fix the position, drag to set the heading, release | `/goal_pose` | `geometry_msgs/msg/PoseStamped` |
| `"Set the initial pose -> /initialpose"` | the same | `/initialpose` | `geometry_msgs/msg/PoseWithCovarianceStamped` |
| `"Select a rectangle -> polygon"` | press at the first corner, drag to the opposite corner, release | `/qar/selected_area` | `geometry_msgs/msg/PolygonStamped` |
| `"Select a circle -> polygon"` | press at the centre, drag to the rim, release | `/qar/selected_area` | `geometry_msgs/msg/PolygonStamped` |
| `"Select a polygon (tap vertices)"` | tap each vertex, then `"Close polygon"` | `/qar/selected_area` | `geometry_msgs/msg/PolygonStamped` |

The topics and the types are the ones that the tools Publish Point, 2D Goal Pose and 2D Pose Estimate of RViz publish, so subscribers of those tools work unchanged and the headset is one more producer on topics that exist. The message is built at run time from the type of its fields, so that no message header is compiled into the plugin. The covariance of an initial pose has the diagonal that the tool of RViz uses: 0.25 for x and y and the square of 15 degrees for the heading, which AMCL reads as the trust in the guess. A circle is published as a polygon of 32 segments. The header of every pick carries the frame of the field `Frame` and the time stamp zero, which tf resolves as the latest available transform and which suits a headset whose clock is not the clock of the robot; the panel never sets a time, so a subscriber that needs the time of a pick has to stamp the message itself.

**Confirmation.** A pick becomes pending when its gesture is complete, and the status says `"waiting for confirmation"`. `"Confirm pick"` publishes it and `"Cancel"` drops it. While a pick is pending, the controller ignores more input, so that what you confirm cannot change under your hand, and a change of the mode, of the target or of the area shape drops the pending pick. `"Close polygon"` finishes the region that the taps collected and needs at least three vertices. `"Publish without confirming"` removes the extra step: the pick is published as soon as you release. Confirmation is on at the start, so that a stray gesture cannot drive the robot. The buttons follow the state: `"Confirm pick"` is enabled only while a pick is pending, `"Cancel"` while a mode is armed, `"Close polygon"` only for the polygon shape, and the fields `Target` and `Frame` only while a mode is armed.

| Target | What it publishes | Needs a ray |
|---|---|---|
| `"Action Point (QarOS scene intersect)"`, the default | the action point that QarOS computed from its own ray, verbatim, in the chosen frame; QuaternAR states that the ray is slightly curved and that the point is the intersection with the scene of the app volume, and the SDK does not document which geometry that ray meets | no |
| `"Ground plane (z = 0) - straight-ray approximation"` | where the straight aiming ray crosses z = 0, so that the answer is always on the floor | yes; without a ray, the reported point is projected straight down onto the plane |
| `"Fixed depth, 2 m along the ray - local approximation"` | the point 2 m along the straight aiming ray | yes |

The action point leads the list because it is the only target that the runtime itself computed, so it is the only one that can be exactly what you saw. It relies on a runtime that reports the intersection of the ray with the scene as the action point, as the header of the installed QAROS states it, and a runtime that reports a point near the hand instead needs another target after you have checked a pick against the scene. [SDK compatibility](SDK_COMPATIBILITY.md#identifying-the-qaros-version) shows how to tell the versions apart. The two other targets are approximations: QuaternAR states that QarOS aims along a slightly curved line, so a straight line cannot reproduce the curve, and the difference was centimetres in every session measured so far. A plane target is a promise about where the answer is, and a navigation goal belongs on the floor. The aiming ray is the one that QarOS gives, from the start point of the gesture, which is your hand, through its action point; the plugin falls back to a straight line from the eye through the hand only when the runtime intersected nothing and the two points coincide.

**Refusals.** A gesture that carries no action point is refused and is never published as the origin of the map. When QarOS intersected nothing, it hands back the start point, which is your hand, as the action point; the plugin detects that case for each gesture, refuses to publish your hand, and counts it as `clicks-on-nothing=`. A hover previews and never commits a pick; only a tap commits. Degenerate geometry, such as a polygon of fewer than three points, is refused with a reason.

The second line of the status label shows the counters of the pointer. It begins with `"AR gestures: rx=%1 (click=%2 hover=%3 other=%4) queued=%5 dropped=%6"` and goes on with `" | picker: seen=%1 used=%2 picks=%3 ignored=%4"`. `"AR gestures: NOT SUBSCRIBED (%1)"` says that no subscription exists, and `"AR gestures: not subscribed yet (connect to QarOS first)"` says that you did not connect yet. The heartbeat carries the same counters on every beat, so that `rx=0` on every heartbeat says that QarOS sends nothing. The first 20 gestures and then one in 50 are also written to the log, with the raw point, the converted point and the pick that the armed target resolved, on lines that begin with `"SPATIAL: sample #%1"`, and a published pick writes `"SPATIAL: published %1 to %2"`.

**Coordinates.** QarOS reports the points of a gesture in the content space of the app, in the units of the scene, and not in metres; the pick therefore takes the change of basis from the room to ROS and nothing else. The change uses the same variables as the camera, `QAR_POSE_WORLD` and its companions, so that a pick lands where the headset looked. The plugin reads where QarOS displays the scene once for each tick and logs every move, because the grab and the pinch of the operator change it, but it does not apply it to a pick.

## Geolocation

The panel can tell QarOS where the origin of the streamed scene lies on Earth, from the GPS receiver of the robot. It subscribes to a `sensor_msgs/msg/NavSatFix` topic, which is `/gps/fix` unless `QAR_PANEL_GPS_TOPIC` names another, with the QoS profile of sensor data, because a reliable subscription would receive nothing from the usual best-effort driver of a receiver. The subscription is armed when the panel loads and does nothing while the topic is silent, and `QAR_PANEL_GEO` set to `off` switches the whole path off.

The callback of the subscription only stores the fix. The render tick applies it, on the GUI thread, so that every call into QarOS stays on one thread, and only while a session is connected. A fix with the status of no fix is ignored. The anchor is set on the app volume of the session from the latitude, the longitude and the altitude, as an ECEF origin with East, North and Up axes, and it moves again only when the position has changed by 2 m or more, because a receiver at 10 Hz would otherwise cost a call of QarOS for every message of jitter. The altitude of a `NavSatFix` is the height above the WGS 84 ellipsoid and not above mean sea level. Without an app volume there is nothing to anchor, and a failure to set the anchor is logged once and stops further attempts, while the streaming goes on without it.

You can try the path with a synthetic fix. The command publishes one fix a second for thirty seconds, and it needs a window that you prepared with the two lines of [AR tools from the ROS graph](#ar-tools-from-the-ros-graph); start it while the panel is connected:

```powershell
python "$env:ROS2_INSTALL_ROOT\Scripts\ros2-script.py" topic pub --rate 1 --times 30 --wait-matching-subscriptions 0 /gps/fix sensor_msgs/msg/NavSatFix "{latitude: 50.0755, longitude: 14.4378, altitude: 200.0}"
```

## Floor plane and scene lighting

**The floor plane.** The Grid display of RViz draws thin line segments only, so the depth picture that the plugin streams would show gaps between the lines. The plugin therefore adds an opaque grey rectangle under every Grid display, so that the depth picture shows a solid floor. The plane lies 1 mm below the plane of the grid, it has the size of the grid, which is the number of cells times the size of a cell, and it follows the frame, the plane (XY, XZ or YZ) and the offset of the grid, and it is visible only while the grid is enabled. It is lit by its own colour only, a grey of 0.4, so that the lights of the scene do not shade it, and it carries a depth bias that pushes it away from the camera, so that the lines of the grid always win. It is drawn before the Grid display and every other display, so that a Grid whose Alpha is below 1 is blended onto the grey and not painted over by it. It is excluded from the ray queries of the scene, so that tools such as Publish Point never pick it. The panel logs a line when it creates or changes a plane and one line when no Grid display exists. `QAR_PANEL_FLOOR_PLANE` set to `off` disables the feature.

**The lighting.** RViz lights its scene with one directional light, a headlight, that it re-aims at its own camera every frame, so that a peer that stands anywhere in the scene would see its shading swing around whenever the operator of RViz orbits the view. While the plugin streams, it adds a rig of lights that is fixed in the world, unless the mode is `off`, and it hides the headlight, unless you keep it, and it restores both when the streaming stops. `QAR_SCENE_LIGHT` selects the rig:

| Value | What it adds |
|---|---|
| `off` | nothing; the lighting of RViz stays as it is |
| `omni` | a raised ambient light and four directional lights on a tetrahedron, so that every surface faces at least one light, with the two brighter lights shining from above |
| `per-peer` | one point light at the head of each connected peer, moved every frame |
| `both` | the two together |

The live mode starts with `both` and the offline preview with `off`, so that the preview and the scripted captures keep the lighting of RViz. A value that is not a mode keeps the default, and the panel logs the mode and the state of the headlight when it loads. `QAR_SCENE_LIGHT_HEADLIGHT` set to `keep` or `on` leaves the headlight on, for comparison only. The brightness is tuned with `QAR_SCENE_LIGHT_AMBIENT`, 0.30 at the start, `QAR_SCENE_LIGHT_INTENSITY`, the brightness of the two lights from above, 0.75, `QAR_SCENE_LIGHT_FILL`, the share of that brightness for the two lights from below, 0.55, `QAR_SCENE_LIGHT_PEER`, the personal light, 0.35, and `QAR_SCENE_LIGHT_RANGE`, the attenuation range, where 0 means no falloff with distance. A fill of 1.0 gives uniform light without any shape, and a fill of 0 lights from above only.

## Offline preview mode

Without `QAR_PANEL_LIVE_STREAM` the panel runs without QarOS: the simulated peers that the panel itself provides replace the session, and nothing is sent to QarOS. The preview shows that the plugin loads, that the render path works on the real scene of RViz, and that several peers can be rendered in one batch. After `"Start Qar"` the state label says `"Qar runtime: RUNNING (offline preview)"`. `"Add simulated peer"`, in the group `"Simulated peers"` of the tab `Diagnostics`, which the preview always shows, adds an entry named `"mock-peer-%02u"` to the list, with its size and its frame rate, and the mark `"STREAMING"` appears on an entry whose stream runs. `"Start stream"` and `"Stop stream"` act on the selected entry and `"Remove peer"` removes it.

The script is run from the folder of the clone, so go there first:

```powershell
Set-Location "$env:QAR_ROOT\src\qar_rviz_plugin"
```

The script `scripts\run_rviz_with_plugin.ps1` starts RViz with the configuration `qar_streaming_dev.rviz`, which loads the panel, in this mode:

```powershell
.\scripts\run_rviz_with_plugin.ps1
```

The buttons `"Capture offscreen frame"` and `"Capture stereo pair"` of the tab `Diagnostics` write pictures of the scene without QarOS. The first renders the scene of RViz into a colour target and a depth target and writes the files `_color.png`, `_depth.png`, `_depth.f32` and `_capture.txt`, with the prefix `qar_offscreen_` and the time in the current folder, or with the prefix in `QAR_PANEL_AUTOCAPTURE` when that is set. The second needs a simulated peer whose stream runs, and writes the colour and depth pictures of the left and the right eye and the file `_stereo.txt`, with the prefix `qar_stereo_` and the time. The four scripted modes of the script, which write a result file and quit RViz, are described in [Scripted checks in a window](TESTING.md#scripted-checks-in-a-window). The five scenes in `qar_rviz_streaming/config/test_scenes` are test content for this mode and for the live mode:

| Scene | Content | Publisher |
|---|---|---|
| `scene1_grid.rviz` | the grid | none |
| `scene2_grid_tf.rviz` | the grid and a tree of transforms | `scripts\publish_test_tf.py` |
| `scene3_grid_marker.rviz` | the grid and markers | `scripts\publish_test_markers.py` |
| `scene4_grid_robot.rviz` | the grid and a small robot model | `scripts\publish_test_robot.py` |
| `scene5_grid_pointcloud.rviz` | the grid and a point cloud | `scripts\publish_test_pointcloud.py` |

The publishers are synthetic and need no data of yours. The pages of the AR tools have a synthetic publisher of their own, `scripts\publish_template_topics.py`, which [AR tools from the ROS graph](#ar-tools-from-the-ros-graph) describes. `scripts\play_demo_rosbag.ps1` records the four publishers for 12 seconds into a bag in `%TEMP%\qar_demo_rosbag` when no bag exists there, and plays the bag in a loop. The script stops the recorder itself, and a recorder that is stopped that way writes no `metadata.yaml`, the index that every `ros2 bag` command needs. So the script writes the file before it plays the bag, with `ros2 bag reindex` and the storage `sqlite3` first and, when that leaves no file, with `scripts\rosbag_write_metadata.py`. A folder that holds a `.db3` file and no `metadata.yaml`, which an interrupted run leaves, is not recorded over: the script writes the missing file and plays that bag. rosbag2 records only into a folder that does not exist yet, so a `-BagDir` that exists and holds no bag makes the recording fail, and the warning of the script says so. When no bag comes of the recording, or the file cannot be written, the script runs the publishers directly, without a bag. RViz ends with the exit code 0xC0000409 as soon as the robot description of scene 4 reaches the Robot model display while the folder of `rviz2.exe` holds no `tinyxml.dll`, which the release of the distribution does not ship; the script `scripts\fix_missing_tinyxml_dll.ps1` of [Repairs to the ROS 2 Windows distribution](INSTALL.md#repairs-to-the-ros-2-windows-distribution) builds the file, and [RViz and plugin problems](TROUBLESHOOTING.md#rviz-and-plugin-problems) lists the symptom.

## Diagnostics view and status lines

The tab `Diagnostics` shows what the panel knows and what it did. The label `"DisplayContext: (not initialized)"` is replaced by a summary of the display context that RViz gave the panel and of its Ogre scene: whether the context and the scene manager are valid, the number of cameras, the root children of the scene and the frame count. `"Refresh diagnostics"` updates that summary and the readout of the AR panels, and writes a line that begins with `"Diagnostics: streaming=%1"` and one line for each stream. The log view at the bottom of the tab keeps the last 2000 lines of the panel, each with the time of day, and the same lines go to the standard error of RViz with the prefix `[qar-panel]`, which is where the launcher keeps them in the file `rviz_live_<stamp>.err.log`. The label `"Last error: <none>"` in the strip turns red and shows the last error, which is also logged with the prefix `ERROR:`, and a later successful action clears it.

The button `"Start test markers"` starts a publisher of test markers, the script `publish_test_markers.py`, which publishes a small marker array on the topic `/qar_test_markers` for the test scenes, and the button then reads `"Stop test markers"`. What the publisher prints goes to the log with the prefix `"TEST MARKERS:"`, one line a second at most. The button is grey, and its tool tip says what is missing, unless `QAR_PANEL_TEST_MARKERS_PYTHON` and `QAR_PANEL_TEST_MARKERS_SCRIPT` name files that exist. Both launchers set the two variables when they find python and the script, and their parameter `-TestMarkers` also starts the publisher together with RViz.

Four readouts show the state at a glance, and each has its own section: the State line, which the first line of the strip repeats, for the connection in [Connecting and pausing](#connecting-and-pausing), `"AR panels: none"` in [AR GUI panels](#ar-gui-panels), `"AR tools: none"` in [AR tools from the ROS graph](#ar-tools-from-the-ros-graph), and `"Spatial: off"` in [Spatial picking](#spatial-picking). Every 2 s the panel writes the heartbeat, which has the beat of the timer, the streams, the panels, the pointer and the displays of images in one line; `QAR_PANEL_HEARTBEAT_S` sets the period and 0 switches it off. The log view of the panel does not survive RViz, and the heartbeat is the line in the log file that tells you most about a run, so read it first when something stalls: `tick_fps=` far below the rate of the stream, or a `max_gap=` of hundreds of milliseconds, says that the GUI thread of RViz was blocked. [The heartbeat line](LOG_REFERENCE.md#the-heartbeat-line) explains every field, [Status lines](LOG_REFERENCE.md#status-lines) the readouts, and [Reading the logs](TROUBLESHOOTING.md#reading-the-logs) the first checks.
